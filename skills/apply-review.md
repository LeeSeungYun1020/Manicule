# 리뷰 반영

[공통 규칙](skills.md)을 적용하고 구현 세션에서 이어가는 것을 기본으로 한다. 별도 세션에서 요청받으면 PR 설명·전체 계획 문서의 관련 요구사항·리뷰와 답글·코드·검증 결과로 문맥을 확인한다. 요청한 PR이 열려 있고 리뷰가 있는지 확인한다. 게시 계정은 `LeeSeungYun1020`이다. 로컬 diff 의견은 GitHub 조회·push·게시 없이 해당 수정 절차만 적용한다.

## 분석과 수정

1. [GitHub 조회 명령](github.md)으로 PR 정보·변경 파일·미해결 인라인 스레드와 답글·리뷰 본문·일반 PR 댓글을 확인한다. [작업 디렉터리 규칙](skills.md#작업-디렉터리)에 따라 같은 브랜치는 갱신 후 사용하고, 다른 브랜치이면 별도 워크트리에서 진행한다.
2. 미해결 지적·질문을 검토하고 같은 근본 원인은 그룹으로 묶는다. 그룹별 방향을 한 번 요약하며 각 의견의 유형·ID·URL과 처리 결과를 유지한다. 일반 댓글과 리뷰 본문도 후속 답변·코드에서 해결 근거가 확인되는 항목만 완료로 판단한다. 이미 해결한 의견은 다시 처리하지 않는다.
3. 승인된 수정 범위는 그룹 단위로 [code-change.md](code-change.md)에 따라 구현·검증·commit한다. 그룹 안에서 같은 변경을 코멘트마다 반복 설명하거나 승인받지 않는다. 대안 선택이나 범위 확대가 필요할 때만 질문한다.
4. 최종 변경 상태에 필요한 검증 결과가 있는지 확인한다. 입력이 같고 이미 성공한 검증은 반복하지 않는다.
5. 계정 확인 후 PR head 원격·브랜치로 push한다. `gh pr checks <PR> --json name,state,link`로 CI 결과를 확인한다.

## 답글

1. 의견마다 수정 내용·수정하지 않은 이유 또는 요청받은 세부 구현 근거를 간결하게 작성한다. 사용자가 답글 사전 검토를 요청했다면 게시 전에 확인한다.
2. 게시 직전 대상 코멘트·답글 상태를 확인해 중복 답글을 피한다. 분석에서 확보한 코멘트 ID를 사용한다.
3. 인라인 답글은 `body`를 담은 JSON 파일을 만들고 `gh api -X POST repos/:owner/:repo/pulls/<PR>/comments/<comment_id>/replies --input <답글.json> --jq '{id,in_reply_to_id,body,html_url}'`로 게시한다. 일반 PR comment와 구분한다.
4. 일반 PR 댓글·리뷰 본문에는 원문 URL과 의견 ID를 연결한 답변을 작성하고 `gh api -X POST repos/:owner/:repo/issues/<PR>/comments --input <답변.json> --jq '{id,body,html_url}'`로 게시한다. 같은 답변에 여러 의견을 묶어도 각 원문과 처리 결과는 구분한다.
5. GitHub API가 반환한 답글 ID·부모 코멘트(인라인) 또는 원문 링크(일반 댓글)·본문으로 게시 성공을 확인한다. 게시 여부가 불확실하면 대상 스레드 또는 일반 댓글을 조회한 뒤 재전송 여부를 결정한다. 처리 결과와 검증 상태를 반환하고 종료하며 resolve·승인은 검수 요청 시 수행한다.
