# 코드 리뷰

[공통 규칙](skills.md)을 적용한다. 사용자가 요청한 PR이 열린 상태인지 확인한다. 게시 계정은 `lsy-auto`다.

## 실행

1. [GitHub 조회 명령](github.md)으로 PR 상태·base 브랜치·변경 파일·본문을 확인한다. 본문에서 PR의 리뷰 초점·범위·제외 범위·검증·규모 예외를 파악한다.
2. [작업 디렉터리 규칙](skills.md#작업-디렉터리)에 따라 PR head로 작업 디렉터리를 준비·갱신한다. PR 기준 원격의 base 브랜치를 fetch 후 계획을 읽는다.
3. [선택 읽기 기준](../AGENTS.md)에 따라 base 계획의 요구사항·구조·선행 조건·현재 상태와 `plan/order.md`의 PR 분할 기준·해당 레인을 확인한다. PR 본문 내용을 출발점으로 변경 코드·사용부·테스트와 계획 단계의 설계 판단을 독립적으로 검토한다. 본문의 주장은 프로젝트 계획과 실제 변경으로 확인한다. PR이 계획 문서를 바꿨다면 base와 head의 정합성을 확인한다. base 오염·소유권 문제, 새 결함과 사이드이펙트를 점검한다. 계획 단계로 생성된 로컬 작업 계획 파일은 요구하지 않는다.
4. 독립 검토 후 기존 리뷰와 대조한다. 확인되지 않는 세부 근거만 질문하고 구현자의 답변도 실제 변경과 대조한다. 같은 근본 원인의 지적을 합치고 이미 등록된 문제는 반복하지 않는다.
5. 인라인 의견은 `event: COMMENT`와 `comments` 배열을 가진 임시 JSON 파일에 모은다. 각 항목은 `path`, `side`(`LEFT`/`RIGHT`), diff에 포함된 실제 `line`, `body`를 지정한다. 전체 요약·칭찬은 넣지 않는다.
6. 계정과 PR head를 확인하고 `gh api repos/:owner/:repo/pulls/<PR>/reviews --method POST --input <리뷰파일> --jq '{id,state,commit_id,html_url}'`로 제출한다. JSON의 `commit_id`에는 검토한 대상 SHA를 지정한다. head가 바뀌었다면 영향 코드와 라인을 다시 확인한다. 지적이 없으면 빈 리뷰를 게시하지 않는다.
7. 인라인으로 표현할 수 없는 PR 범위 문제만 `gh pr comment <PR> --body-file <의견파일>`로 게시한다.
8. PR과 무관한 기존 문제로 수정을 요구하지 않는다. 재현 가능한 개선점은 `gh issue list --state all --search '<검색어>' --json number,title,url`로 중복을 확인하고 없으면 별도 이슈로 게시한다. 결과 한도에 도달하면 페이지를 추가 조회한다. 이슈 게시 실패는 리뷰를 막지 않고 후보와 원인을 보고한다.
9. 게시 결과를 확인하고 임시 파일을 정리한다. 발견 사항·게시 결과·검토 제약을 반환하고 종료하며 직접 수정하거나 반영 단계로 전환하지 않는다.
