# 작업 절차

## 진입점

전체 흐름은 계획 → 구현 → 리뷰 → 반영 → 검수다. 사용자가 요청한 단계만 수행하고 결과를 반환하며, 이전·다음 단계로 자동 전환하지 않는다. 이전 단계의 필수 입력이 없으면 필요한 항목과 이유를 사용자에게 요구하고 해당 작업을 보류한다. 공통 규칙과 요청한 단계의 문서·참조된 세부 절차만 읽는다. 계획·리뷰·검수는 각각 별도 세션에서 진행하고, 반영은 구현 세션에서 이어가는 것을 기본으로 한다.

| 단계 | 작업                                         | 입력             | 결과            | 절차                                                                                 |
|----|--------------------------------------------|----------------|---------------|------------------------------------------------------------------------------------|
| 계획 | plan 문서·기존 코드 확인, 다음 작업·범위 설정, 구현 계획 파일 작성 | 목표 또는 대상 레인    | 계획 파일         | [plan-work.md](plan-work.md)                                                       |
| 구현 | 계획 파일에 따라 구현하고 PR 생성                       | 계획 파일          | 구현, 검증, PR 결과 | [work.md](work.md), [code-change.md](code-change.md), [pr-create.md](pr-create.md) |
| 리뷰 | 구현 내용과 영향 코드 리뷰                            | 대상 PR          | 리뷰 게시 결과      | [code-review.md](code-review.md)                                                   |
| 반영 | 리뷰 타당성 검토 후 수정                             | 대상 PR 또는 수정 지시 | 수정, 검증, 답변 결과 | [apply-review.md](apply-review.md), [code-change.md](code-change.md)               |
| 검수 | 반영한 수정 내용 검수                               | 대상 PR          | 리뷰별 해결, 승인 여부 | [review-check.md](review-check.md)                                                 |

PR 생성만 요청받으면 `pr-create.md`를 사용한다.

## 공통 규칙

- 문서는 [AGENTS.md](../AGENTS.md)의 선택 읽기 기준을 따른다. PR 분할·의존성·소유권은 `plan/order.md`, 현재 상태와 다음 범위는 `plan/current.md`가 기준이다.
- 범위·제외 범위·완료 기준을 간결하게 알리고 승인된 범위는 계속 진행한다. 새 의사결정·범위 확대 또는 사용자가 지정한 승인 조건에 해당할 때만 질문한다.
- 파일별 전체 코드·diff 재출력과 단계 번호 나열을 생략한다. 의미 있는 발견·변경 결과·검증·남은 제약을 보고한다.
- 기존 변경을 보존하고 현재 작업 파일만 stage한다. 의존성·소유권 충돌은 구현 전에 해결한다.
- Android/Kotlin 변경·리뷰에만 관련 공식 가이드와 [Kotlin 컨벤션](https://kotlinlang.org/docs/coding-conventions.html)을 적용한다. `android-cli` 스킬이 없으면 공식 문서를 조회하며 스킬 전체 설치를 요구하지 않는다.
- 새 사용자 의사결정과 이유가 계획 또는 PR 본문에 기록되지 않는 경우에만 [history 작성 규칙](../history/README.md)을 읽고 기록한다.

## 작업 디렉터리

특정 AI 도구의 기능을 전제하지 않고 Git 명령을 기준으로 한다. 명령은 선택한 작업 디렉터리의 루트에서 실행하며 다른 세션이 사용하는 로컬 체크아웃의 브랜치를 전환하지 않는다.

1. `git status --short`, `git branch --show-current`, `git worktree list --porcelain`으로 기존 변경·현재 브랜치·워크트리를 확인한다. PR은 브랜치 이름뿐 아니라 head 저장소와 commit도 대조한다.
2. PR 작업은 브랜치·워크트리 선택 전에 `git fetch <PR기준원격> pull/<PR>/head`를 수행한다. `git rev-parse FETCH_HEAD`와 조회한 PR head SHA가 일치하는지 확인하고 해당 SHA를 대상으로 사용한다. 다르면 PR head를 다시 조회하고 fetch해 일치시킨다.
3. 현재 브랜치가 대상 작업/PR 브랜치와 같으면 그대로 진행한다. PR 갱신은 변경이 없는 상태에서 `git merge --ff-only <대상SHA>`를 수행한다. 분기·충돌·미커밋 변경이 있으면 자동 reset·stash로 맞추지 않는다. 자신의 구현 변경은 보존하며, 리뷰·검수에는 미커밋 변경이 섞이지 않은 대상 SHA를 사용한다.
4. 실행 환경이 이 작업 전용 워크트리를 이미 제공했고 기준 commit이 맞으면 재사용한다. detached HEAD도 정상이다. 구현은 그 안에서 `git switch -c ai/<작업>`으로 브랜치를 만든다.
5. 다른 브랜치의 로컬에서 시작했다면 `git worktree add --detach <새경로> <대상SHA>`로 별도 워크트리를 만든다. 실행 환경이 동등한 기능을 제공하면 사용할 수 있으며, 이후 명령의 작업 경로는 생성된 경로로 지정한다. 기존 변경은 옮기지 않는다. 이미 잘못된 위치에 작업한 변경이 있으면 이전 범위를 먼저 확인한다.
6. 리뷰·검수는 detached HEAD를 유지할 수 있다. 반영은 워크트리에 별도 `ai/<작업>` 브랜치를 만들고 PR head 저장소의 원래 브랜치로 `git push <head원격> HEAD:<PR브랜치>`한다. 다른 워크트리가 점유한 브랜치를 강제로 체크아웃하거나 force push하지 않는다.

## 조회와 검증 결과

- 파일은 `rg --files`, 문서는 제목 검색 후 관련 구간을 읽는다. 불변 조건·예외·호출부는 누락하지 않는다.
- 긴 출력은 로그로 보관한다. 성공 시 명령·종료 상태·로그 경로, 실패 시 관련 오류를 확인한다. 종료 코드를 보존한다.
- 독립 조회는 묶고 계정 변경·push·게시·resolve·approve는 결과를 확인하며 순차 실행한다. 권한·게시 실패는 중단하고 보고한다.
- GitHub 작업에서는 [조회·게시 명령](github.md)을 읽는다. 계획·로컬 구현 단계에서는 읽지 않는다.
