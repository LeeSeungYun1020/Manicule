# 4bea968 — docs: 버티컬 슬라이스 병렬 작업 계획 개편

**Files**: `plan/order.md`, `plan/current.md`, `plan/structure.md`

## 결정

- 공용 모델·API 의미 계약만 선행하고, 기능별 작업 레인은 Data → Domain → UI → 테스트를 관통한다.
- 작업 레인은 병렬 배정 단위로 두고, 하나의 사용자 행동을 검토하는 여러 PR로 나눈다.
- `core:notifications`는 Domain의 `ReminderScheduler` 계약을 구현하며 `core:data` Repository를 직접 사용하지 않는다.

## 이유

- 전체 단계 완료를 기다리는 방식보다 충족된 `depends_on`만으로 시작하는 편이 독립 기능의 병렬 처리량을 높인다.
- 문자열·아이콘·Gradle 같은 단순 추가 충돌을 허용하는 비용보다 공용 API의 동시 의미 변경과 기능 중복 구현을 막는 편이 중요하다.
- 기능 전체를 한 PR로 만들면 리뷰가 비대해지므로, 레이어별 분리 대신 실행 가능한 하위 사용자 흐름으로 세분화한다.
- 알림 인프라가 서재 Repository를 직접 알면 도메인 결합이 생기므로 메시지 생성은 Domain UseCase에 둔다.
